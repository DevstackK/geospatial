Use the app

Pipeline and IQGEO rules
  1. Confirm the source and target tables. Identify the Gcomm Oracle source tables, IQGEO Oracle target tables, primary IDs, geometry columns, status fields, and parent-reference fields. Put those names into DB tests and IQGEO rules.
  2. Run read-only DB tests. Open DB tests, confirm the Gcomm and IQGEO table names, copy the read-only test pack, and run it from the backend runner to verify connectivity, table access, IDs, status values, and geometry quality.
  3. Review the DB test results. Check row counts, null IDs, null geometries, duplicate IDs, invalid Oracle Spatial geometries, SRID distribution, existing IQGEO IDs, and status values that may indicate redundant data.
  4. Open IQGEO rules. Define Gcomm source tables, IQGEO target tables, staging tables, clean/reject/redundant tables, required fields, asset types, statuses, geometry rules, and parent reference rules.
  5. Decide how each failure is classified. Keep valid rows as approved, send safe automatic fixes to fixed, block hard failures as rejected, hold uncertain records as quarantined, and move retired or duplicate records to redundant.
  6. Download the rules YAML. Save it as config/iqgeo-rules.yaml. This is the strict import gate for deciding approved, rejected, quarantined, redundant, and review records.
  7. Use Pipeline for execution config. Set the staging/export/target tables and commands that the backend runner will use for dry-run and execute mode.
  8. Download the pipeline YAML. Save it as config/oracle-output.yaml in the backend project.
  9. Run dry-run first. Review the generated validation report, reject/redundant counts, SQL plan, and audit before allowing execution.
  10. Execute only after review. Run execute mode only after sign-off on row counts, changed fields, reject reasons, redundant classifications, and staging-table behavior.
  11. Import only approved records into IQGEO. The IQGEO target should receive clean and approved rows only. Rejected, quarantined, redundant, and review rows stay outside the target import path with audit reasons.

Best ways to connect the databases

Recommended architecture
1. Backend runner near Oracle

Best option. Run the Python cleaner on a VM, Cloud Run, ECS, Render worker, or internal server that can reach both Gcomm Oracle and IQGEO Oracle over private networking or VPN.

recommended for production
2. Internal network or VPN

Keep Oracle closed to the public internet. Allow the backend runner through VPN, private subnet, bastion, or fixed egress IP rules.

private access only
3. Vercel as UI only

Use Vercel to host this app and generate configs. Do not put Oracle passwords in the browser and do not run long migration jobs in frontend code.

config UI, not DB runner
4. Local operator mode

Useful for first tests. Run the backend from a laptop or desktop already connected to the client VPN, then move to a server once rules are proven.

good for pilot testing

Important limits

The browser app does not connect to databases or store credentials. It generates config. The Python backend does the database work.

For millions of records, keep execution close to the databases and run validation inside Oracle or a backend worker with stable Oracle connections.
